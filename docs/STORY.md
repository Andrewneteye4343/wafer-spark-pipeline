# 專案口述稿：wafer-spark-pipeline

> 用途：面試／電話初談時講這個專案。全部數字都可在 repo 的 `docs/PERFORMANCE.md`
> 與 `run_history.jsonl` 找到。**不宣稱「親手寫每一行程式」**——講的是問題定義、
> 架構與方法選擇、驗證標準的設計，以及實際踩到的坑。

## 3 分鐘版

### 0:00–0:30 一句話定位

「我做了一個晶圓廠的資料管線：從 Oracle 抓 8 張表，在 Docker 上跑 Spark，
分成 bronze／silver／gold 三層，中間加一道資料品質閘門，最後產出每日 HTML 報表。
資料量是 200 萬筆製程事件、7.8 萬片晶圓。」

### 0:30–1:20 為什麼是這樣設計（三點）

「設計上我處理三件事。

**第一，為什麼分三層。** 來源改了或我的程式改了，都可以從 bronze 重跑，
不必重新打 Oracle。silver 做清理與標準化，gold 只放指標。

**第二，資料品質誰把關。** 我把 DQ 閘門放在 gold **之前**——壞資料不可以先變成
人人看得到的報表。四條規則：孤兒外鍵、時間順序、規格內比例、缺日。
失敗時不是丟掉，是把壞列寫進隔離區，而且用 exit code 2 跟程式錯誤區分開。
為什麼要分？因為『資料不好』該找製程或資料擁有者，『程式壞掉』該找工程師，
混在一起，值班的人會去修錯的東西。

**第三，重跑會不會算錯。** 我定義的冪等不是『重跑不會報錯』，是
**重跑後每一張表的內容完全相同**。所以我做了一支指紋程式，把 gold 的列數
與數值總和印出來，兩次執行必須一字不差。」

### 1:20–2:10 一個實際踩到的坑（誠實的技術細節）

「我舉一個具體的例子。我原本 silver 用 INNER JOIN 把事件接上晶圓資料。
做 DQ 測試時，我故意注入 20 筆孤兒事件——結果管線在 silver 就掛了，
錯誤是列數不符。原因是 INNER JOIN **默默把孤兒列丟掉了**。

這件事讓我改設計：silver 改用 LEFT JOIN，讓列活下來，讓 DQ 去判定與隔離。
理由是——**資料該不該丟，是資料品質的決定，不是 join 的副作用。**」

### 2:10–2:50 效能：用數字而不是形容詞

「效能上我做對照實驗。小表廣播後 shuffle 寫入是 0 MB，改成排序合併變 9.8 MB。
但耗時差在誤差範圍內，所以我寫的結論是『在這個資料量下 join 不是瓶頸』，
沒有寫成『廣播快兩倍』。

分區數從 2 調到 8 快 20%，8 到 200 之間的差距只有 0.16 秒——那是雜訊，我照實寫雜訊。」

### 2:50–3:00 收尾

「這個專案給我的結論是：資料工程難的不是把數字算出來，是
**證明算出來的數字是對的、而且明天再跑一次還是對的**。」

## 30 秒極簡版

「我做過一條 PySpark 資料管線：Oracle 進 bronze、清成 silver、加一道 DQ 閘門、
輸出 gold 指標與每日報表，200 萬筆製程事件。
重點是失敗分三態、DQ 在報表之前、以及用指紋驗證重跑結果完全相同。
效能部分我量了 join 策略與分區數，也照實記錄哪些改善在誤差內。」

## 十個可能的追問

**Q1 為什麼不用 pandas / 單機腳本就好？**
資料量 200 萬列已經讓 pandas 吃記憶體；而且我需要排程、重跑、分層落地。
Spark 的價值是把「重算某一天」變成可重複操作，不是速度。

**Q2 為什麼 DQ 放在 silver 之後、gold 之前？**
silver 之前的資料還在做型別轉換，檢查會誤報；gold 之後已經被人看過，擋不住。
放在中間是唯一能「攔下但還沒發布」的位置。

**Q3 孤兒外鍵為什麼不是直接過濾掉？**
過濾等於默默改資料。隔離後留下證據，才能回頭問「為什麼會生出這 20 筆」。

**Q4 良率怎麼算？**
`SUM(pass die) / SUM(all die)`。不是各 bin 比例取平均——那會讓小 bin
與大 bin 權重相同，答出錯的數字。

**Q5 在製品（still in process）怎麼算？**
`COUNT(*) - COUNT(out_ts)`。用 `MAX(out_ts)` 會忽略 NULL，
給出「全部已出站」的假象，而產線上這正是最貴的誤判。

**Q6 怎麼確認 Spark 算的和 SQL 算的一致？**
gold 產出後，用 12 片晶圓逐筆對照 `oracle-sql-lab` 的 SQL 結果，
12/12 完全相符；每個批次的 event 數與每站事件數也比對過。

**Q7 重跑為什麼不會重複計算？**
生成資料用固定 seed 與固定時間基準；silver 對主鍵去重；寫入是 overwrite；
最後用指紋驗證兩次執行完全相同。

**Q8 效能怎麼調的？**
先讀實體計畫再調：`PartitionFilters` 與欄位裁剪確認下推；join 策略比較四種；
分區數掃 2/8/32/200。結論是這個資料量下 join 不是瓶頸，分區 8–32 就夠。

**Q9 資料量變 100 倍怎麼辦？**
現在是單機 2 cores，100 倍要先換掉三件事：儲存改分散式（S3/HDFS 或 Delta）、
executor 數量與記憶體、以及把 DQ 的失敗處理改成非阻塞（隔離 + 告警，不整條停）。
我會先量 shuffle bytes 與 stage 時間，再決定要不要動架構。

**Q10 這些程式是你自己寫的嗎？**
架構與方法是我決定的：三層切法、DQ 規則與它的位置、失敗分三態、
冪等的驗證方式、效能實驗的設計。實作我大量使用現代工具加速，
但每一個設計選擇我都能解釋為什麼，也踩過並修過它們帶來的錯。

## 與台積電 IMC（智慧製造）的對應

| JD 需求 | 這個專案的證據 |
|---|---|
| big data technologies | Spark（PySpark）2M 列管線、分區策略、實體計畫分析 |
| 資料管線／排程 | run_pipeline.sh + scheduler 容器、run_history 執行歷史 |
| 資料品質 | 4 條 DQ 規則、隔離區、三態失敗分類 |
| optimization / scheduling | 效能實驗：join 策略、分區數、膝點量測（不是刷題型演算法） |
| dashboard / 報表 | 每日 HTML 儀表板（KPI + 4 圖）、狀態顏色、run 分隔 |
| SQL / 資料庫 | 另一支 Oracle 專案：8 表模型、視窗函數、執行計畫、1Z0-071 課綱 |
